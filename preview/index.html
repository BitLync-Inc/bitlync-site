The product

How Bitlync works

One model underneath. Your product uses one API. The MSP connects their own tools.

01 — Your product integrates once

One schema, every vendor

Write against one model: tickets, companies, contacts, and agreements, using Bitlync words. Devices too, where that connector exists. No per-vendor branches in your codebase.

02 — Customers connect themselves

Self-serve, guided, validated

The MSP pastes their own PSA or RMM keys. You never hold those credentials. ISVs start with docs and a sandbox, not a wiring guide per MSP.

03 — Act through the stack

Read and write, safely

Open a ticket or update a device through the API. Writes that already support it take dry_run and an idempotency_key. Creating a leftover PSA company in the ISV is not shipped yet.

Everything that comes with an integration

Every layer you'd otherwise build, bundled

These are not add-ons. Caching, retries, validation, and the vault ship with every connection.

Caching

Reads come from our synced store. They are fast and do not spend the vendor rate budget. Each response says where it came from and when it was synced.

Rate-limit handling

We pace every call against each vendor's real limits so your product never trips them by accident.

Retries

Transient vendor failures are retried with backoff. You see one clean result, not a flaky upstream.

Honest delivery status

Deduped and retried. No silent drop. An acknowledged write cannot double-write. A throttled one returns a real Retry-After.

De-duplication

Idempotency keys on writes that support them mean a retry does not double-create a ticket.

Validation

Payloads are checked against each vendor’s rules before they leave. Errors show up in your request, not in an MSP’s PSA.

Credential vault

The MSP pastes their own PSA or RMM keys. Those credentials sit in a per-tenant vault. Your product never holds them.

Customer map

A sure match maps automatically. A leftover PSA company is an ask to create in the ISV. Ambiguous stays unmatched. No silent create. The create hop itself is not shipped yet.

Identity hold

Unmatched records can be held in quarantine until someone releases them.

Health + incidents

Connection status and an audit log are in the product. The vendor-health board on this page is a mockup.

Grants, not shared credentials

You own the connection. Vendors get grants.

You connect your PSA or RMM to Bitlync once. That connection is yours. Each vendor gets a separate, scoped grant. You enter the credential on our side. It stays in an isolated per-tenant vault. The vendor never sees it. Revoke a grant and that vendor is gone. Your connection stays yours.

Overview

Docs and a sandbox. That is how ISVs start.

Write once. Connect to many. Hold a key, call a seeded tenant, then have the MSP paste their own keys. Try it out is Coming. There is no public sandbox URL on this page.

You sell software to MSPs (managed service providers). They run IT for other companies, on a stack they already chose. Winning those deals is much harder if you cannot connect to that stack.

  • PSA — their business system. Customers, tickets, service desk, projects, invoices, agreements.
  • RMM — their device system. Inventory, monitoring, patching, access.
  • Documentation — the detailed record. Passwords, networks, and what happened at that customer, linked to the PSA company and the RMM assets.
  • Commerce — where they buy licenses (direct or through a distributor) and then bill the customer.

Those tools do not share one API. Every MSP picked a different mix. Bitlync is one API with one shape. You write once. The MSP pastes their own keys. You do not hold them.

Caching / store-served reads

Reads come from the synced store for that MSP tenant. One sync fills the store. Every ISV on that tenant reads the same copy.

Mechanism

The caller asks for tickets, devices, or other listed reads. Bitlync answers from the store. That path does not spend vendor budget. live=True is the priced escape hatch when a store read is not enough. There is no public live-read URL on this page.

What the caller sees

The response names the store and the last sync. Fields are served_from and last_synced_at.

store-served read
{
  "served_from": "store",
  "last_synced_at": "2026-07-11T14:03:22Z",
  "data": [{
    "status": "in_progress",
    "source": "psa",
    "raw": {}
  }]
}

Not shipped

No public live-read URL. No live-read host on this page. Try it out is Coming.

Rate limits

One sync per MSP tenant serves every ISV. Writes to the vendor are paced to that vendor’s real limit. The ISV is not asked to guess a vendor quota.

Mechanism

ISV-facing: 600 req/min times the number of connected MSPs. There is no daily cap. The per-minute rate is the limit. Hit it and the API returns a real 429 with Retry-After. There is no silent throttle.

What the caller sees

A 429 you can branch on. The header is the wait. Do not treat a delayed 200 as a throttle.

429 + Retry-After
HTTP 429
Retry-After: 12

{
  "status": 429
}

Not shipped

No silent queue that looks like success. This page does not document a vendor daily cap, and it does not treat the vendor as the villain.

Retries

Transient vendor 429 and 503 are retried with backoff on the Bitlync side of the write.

Mechanism

The caller sends one write. Bitlync retries the vendor when the failure is transient. The caller is not asked to implement vendor backoff for those hops.

What the caller sees

One clean result. If the write still cannot land, the final 429 still carries the vendor Retry-After.

final 429 still honest
HTTP 429
Retry-After: 30

{
  "status": 429
}

Not shipped

No hidden swallow of a vendor 429. No rewrite of a final 429 into a 200.

Honest delivery

Delivery status is visible. Nothing is dropped on the floor to keep a dashboard green.

Mechanism

A write that was acknowledged cannot double-write. A write that was throttled is a real 429, not a delayed success. Dedup and retries sit on this same rule.

What the caller sees

Success means the write landed or was an idempotent replay. Throttle means 429 plus Retry-After.

acknowledged, not doubled
{
  "idempotent_replay": false
}

Not shipped

No silent drop. No “accepted” that later vanishes.

Dedup

Writes that support it take idempotency_key. The same key does not open a second ticket.

Mechanism

Send the key on the write. A retry with that key is a replay, not a new vendor create.

What the caller sees

The replay is marked idempotent_replay.

same key
{
  "summary": "Printer offline",
  "dry_run": false,
  "idempotency_key": "ticket-1"
}

{
  "status": "ok",
  "idempotent_replay": true
}

Not shipped

Keys are not implied on every future write. Only writes that already support idempotency_key.

Validation

The payload is checked against that vendor’s rules before it leaves Bitlync.

Mechanism

A bad field fails on the request you sent. It does not land as a mystery ticket in the MSP’s PSA.

What the caller sees

HTTP 422. Branch on stable code validation.

422 on your request
HTTP 422

{

Not shipped

No “send it anyway and let the PSA reject it.” No extra validation codes on this page.

Credential vault

The MSP pastes their own keys. Those keys sit in a per-tenant vault. The ISV never holds them.

Mechanism

ISVs start with a key that looks like blk_… and header X-API-Key. MSP credentials are entered on Bitlync, not in your frontend.

What the caller sees

Your product sends X-API-Key. It does not send the MSP’s PSA or RMM secret.

ISV auth header

# They sit in the per-tenant vault.

Not shipped

The ISV does not paste MSP creds. There is no shared-secret path that puts PSA keys in your app.

Customer map

A sure match auto-maps. A leftover PSA company with no ISV candidate is an ask: the MSP creates or imports it in the ISV. Ambiguous UNMAPPED is a human match. It is never an auto-create.

Mechanism

Listed identity routes exist: GET /tenants/{tenant_id}/identity/mappings and GET /tenants/{tenant_id}/identity/unmapped. The create-into-ISV hop is not shipped.

What the caller sees

Mapped rows when the match is sure. UNMAPPED when a person has to choose. Creating a leftover PSA company in the ISV returns 501 (OPEN).

Escape hatch

The canonical Bitlync shape is the default. The vendor payload always rides on raw.

Mechanism

Normalize status, source, and the other Bitlync words. Keep the vendor’s original object under raw. Never drop it.

What the caller sees

You can stay on the canonical fields. You can read raw when a vendor word is not in the model.

raw always present

Not shipped

Writes

dry_run defaults true. That is a preview with no side effect. Commit by sending dry_run false.

Mechanism

Preview first. Then commit with the same body and an idempotency_key on writes that support it. If a fan-out is only partial, that failure is explicit. It is never collapsed into a single silent success.

What the caller sees

A dry run does not create a ticket. A commit does. Partial failure is visible on the response, not hidden.

dry_run then commit
{
  "summary": "Printer offline",
  "dry_run": true,
  "idempotency_key": "ticket-1"
}

{
  "summary": "Printer offline",
  "dry_run": false,
  "idempotency_key": "ticket-1"
}

Not shipped

No default-commit write. Creating a leftover PSA company in the ISV is not shipped. Try it out · Coming

Errors

Branch on the stable code. Do not parse a human sentence.

Mechanism

The codes on this page are the codes that exist: 401 auth, 403 tenant, 404 unknown tenant, 422 validation (and request_invalid on a bad sandbox reset), 429 plus Retry-After, 501 unsupported / parked capability, 500 opaque internal_error.

What the caller sees

stable code
HTTP 401  { "status": 401, "code": "auth" }
HTTP 403  { "status": 403, "code": "tenant" }
HTTP 404  { "status": 404 }
HTTP 422  { "status": 422, "code": "validation" }
HTTP 429  Retry-After: 12
HTTP 501  { "status": 501, "code": "unsupported" }
HTTP 500  { "status": 500, "code": "internal_error" }

Not shipped

No extra codes on this page. 500 stays opaque. A parked write is 501, not a generic 500.
